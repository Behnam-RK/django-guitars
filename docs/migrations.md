# Enforcement migrations

## Vocabulary

An **enforcement migration** is a generated migration of `RunSQL` operations, describing what the database **guarantees about the rows** (not schema, already covered by Django's own migrations) for every code path, including ones that never call `save()`. An **enforcement operation** is one `RunSQL` entry: a timestamp trigger (`_updated_at`), a soft-delete rule (`_deleted_at`), an owned soft-delete rule (`OwningForeignKey`), an MTI redirect rule/trigger, a tenant policy (RLS), or a tenant-autofill `BEFORE INSERT` trigger. All six ship from one command sharing discovery, dedupe, scaffolding, digest stamping, and app scoping. The shape of the model *is* the opt-in — no registry.

## Generating them

`makemigrations` is extended to run the generator right after the schema migrations by default, so the two cannot drift (`--check` fails CI if either layer is missing). Set `GUITARS_AUTO_MAKE_MIGRATIONS = False` for the explicit two-command workflow instead. `LOCAL_APPS` names which apps the generator scans — a label matching no `AppConfig.name` scans nothing and `--check` exits 0, not an error.

> ⚠️ With `GUITARS_AUTO_MAKE_MIGRATIONS = False`, plain `makemigrations` does **not** create the rules. Until `makeguitarmigrations` runs and you `migrate`, `.delete()` permanently deletes rows.

## Generated migrations carry their SQL literally

A generated operation contains the statements it runs, not a reference to a library constant — until 1.1.0 the file did `from guitars import sql`, so a migration's *meaning* depended on the installed kit version: the same migration number built `<> 'on'` rules on 1.0.0 but `= 'off'` on 0.7. `guitars.sql`'s names remain a frozen interface for that committed form's sake.

## Idempotency has three layers

1. **A `[DIGEST:…]` marker** on the migration's first line identifies an unchanged *operation set* — if nothing changed, no new migration is written.
2. **Per-operation comment headers** identify which tables are already covered, so a *partially* covered app receives only what it lacks.
3. **A `[SQL:…]` identity** on each header digests that operation's SQL — what makes a changed SQL constant generate its own migration.

The third exists because the first two missed the case that mattered most: the header scan short-circuits before anything is built, so a recognised header read as covered *forever* — how the 1.0.0 soft-delete guard rewrite reached every existing database as nothing at all. A header with **no** `[SQL:…]` predates SQL inlining and reads as stale, regenerated once on 1.1.0.

> ⚠️ **Header strings are frozen.** Reword one and every existing migration stops being recognised, emitting duplicates. `tests/test_header_corpus.py` guards every scanner against the project's own committed migration history.

## Three forms

Each operation is emitted in one of three forms, chosen from what history records — `IF EXISTS`/`OR REPLACE` are claims about *knowledge*:

| Recorded | Form | Why |
| --- | --- | --- |
| nothing | plain `CREATE` | A collision must fail loudly. |
| a different/no `[SQL:…]` | `DROP`+`CREATE`, no `IF EXISTS` | Known to be ours; an unguarded drop reports drift instead of hiding it. |
| `--adopt` | `DROP … IF EXISTS`+`CREATE` | The flag's premise is that nobody knows what the database holds. |

Soft-delete rules and trigger functions are the two exceptions, always `CREATE OR REPLACE` — no instant without a rule, and `DROP FUNCTION` refuses while any trigger depends on it. `--adopt [app_label …]` exists because `create_tenant_policy` is a bare `CREATE POLICY` (no `IF NOT EXISTS`), so an unrecorded-but-real policy used to fail `migrate` with *already exists*. Cannot combine with `--force-rls` — run `--adopt` first.

## Rule names

PostgreSQL dedupes a rule on its name per table, not on what it references, so two operations resolving to one name is a **silent replacement** rather than an error — the second wins, the first relation stops cascading, and `--check` stays green over the loss. Every name folds a schema-qualified table in **length-prefixed** (`('tenant_a', 'events')` and `('tenant', 'a_events')` would otherwise meet). The cascade family adds its FK column plainly: an inbound child with two `CASCADE` foreign keys to one parent keeps the bare `soft_delete_related_<child>` for the first and takes `soft_delete_related_<child>_<fk>` for the rest, which a child table named exactly another child's `<table>_<column>` can claim twice. "For the first" is decided per *call*, and an MTI parent and its child resolve to one `owner_table`, so a model with a `CASCADE` key to each of them claims the bare name twice as well — and reaches the same dedupe *key* doing it, which is why the clash is reported on the relation and not on that key. That spelling shipped in 0.x and **cannot move** — nothing retires a rule, so renaming it would leave every migrated project's old rule live beside the new one — so the generator reports the clash instead of renaming around it, on stderr and as a `--check` failure: one of the two rules does not exist in the database the migration ships to, which is what `--check` is for. A generating run only reports, the files being written by the time it is known. The *owned* family, new in 2.3.0 and free of that history, sizes **every** variable segment — `soft_delete_owned_<n>_<target>_<n>_<fk>`, schema included — so reading each length before its segment leaves no boundary to guess at and no two `(schema, table, column)` triples can reach one name. Sizing only the last segment would not have been enough: it rules out the adjacent split (`('shop_press_kit', 'kit_id')` versus `('shop_press', 'kit_kit_id')`) while `('a_5_b', 'c')` and `('a', 'b_1_c')` still meet on `soft_delete_owned_a_5_b_1_c`. The report covers both families regardless — a proof in one is not a reason to stop watching. The two families' distinct prefixes are what keep them from meeting each other at all.

## Retirement

The three forms above all *assert* an object. **Nothing else is ever retired**: no rule or trigger of the other five kinds is dropped when the model stops calling for it, so removing the field behind one makes Django's `RemoveField` fail at `migrate` (`rule … depends on column`) and relaxing one — a `CASCADE` foreign key made `SET_NULL`, an `OwningForeignKey` made plain — leaves the rule live with `--check` green. Both want a hand-written `DROP RULE` in the same migration. Tenant autofill triggers are the one kind that can also be **retired**, because their dedupe key is `(table, function)` and the function is named after the `(dimension, column)` pair — so renaming `GUITARS_TENANT_FIELD` or a `db_column` mints a new key and orphans the old trigger, which then dereferences a dropped column and fails *every* `INSERT` on the table. A key recorded but no longer required emits `HEADER_TENANT_AUTOFILL_RETIRED` and a bare `DROP TRIGGER` (`reverse_sql` recreates it), and the scan **subtracts** that key — the only place it does, which is what makes a later re-adoption emit a plain `CREATE` rather than a drop against nothing. Idempotency is the set difference alone, not a digest comparison. Two deliberate refusals: a table no local model maps to is *named, not retired* (no app to migrate into, and no migration-state graph to ask which app owned it), and an orphaned **function** is named rather than dropped (it is inert, `DROP FUNCTION` must follow every dependent trigger, and a scoped run cannot prove an out-of-scope app has none). `--adopt` uses `DROP … IF EXISTS` but never re-retires an already-retired key, since re-asserting an *absence* would grow history on every run.

## Singletons, cross-app cascades, scaffolding

`set_updated_at()`/`set_parent_updated_at()` are shared functions with one migration each in `TRIGGER_FUNCTION_APP`, kept separate so adding MTI support doesn't re-digest the single-table function migration. Tenant autofill hosts its functions there too, but keyed by name rather than as singletons — one per distinct `(column, GUC)` pair, which is **one** for a typical project since `GUITARS_TENANT_FIELD` is project-wide. Its trigger header names the function it calls, so an app depends only on the function migrations its own triggers use. The singleton is still ensured in its host app even when a scoped run named a different app, because every other enforcement migration depends on it. A cascade rule is written into the **parent** model's migration; if that app isn't in a scoped run, it's skipped with a warning naming the app to include — the accepted "pragmatic scope" tradeoff. An *owned* rule has no such gap in **where it lands**: it fires on the declaring model's own table, so it always goes into the app being scanned. Since 2.4.0 it has a different one — its last-owner guard reads every owning column across the whole registry, so a model added in an app that *is* in scope moves the rule text of one that is not, which a scoped run will not regenerate. Warned, not escalated: an unscoped run (what CI runs) re-derives every rule. A co-owner arm also makes the rule reference a table in another app, and PostgreSQL resolves table references when it parses a rule action — so that table must exist by the time the migration runs. **Assumed, not enforced:** no dependency edge is emitted. Generation order is not application order — across apps Django orders by explicit dependencies and then by leaf — so where an arm reads an app nothing else depends on, a fresh `migrate` can reach the rule first and fail with `relation ... does not exist`. Deliberate: an edge into an app the models have no relation to can close a cycle in the migration graph, which bricks `migrate` entirely rather than in one order. The remedy is a hand-written `dependencies` entry on the generated migration, or migrating that app first. The graph of ON UPDATE rules the generator refuses cycles from is read over the **whole** registry rather than the apps in scope — scoping narrows what gets written, never which rules exist, and a cycle detected from half the models would be a different set of refusals run to run. The generator rewrites a `makemigrations --empty` scaffold; one that fails after Django wrote it is left in place, carrying no `[DIGEST:…]`, so a later run can't mistake it for coverage.

## Staging row-level security

`GUITARS_RLS_FORCE` defaults to `True`. For a retrofit onto a populated database, ship inert (`GUITARS_RLS_FORCE = False`) and force later via `--force-rls`; `force`/`exempt_roles` are **literal arguments**, never read from settings at migrate time. A tenant policy's SQL depends on a variable `{dimension: column}` mapping, so its header carries a `[POLICY:<digest>]` identity separate from `[SQL:…]` — a changed identity emits a **replacement**, catching a model that gained a dimension while `--check` would otherwise report clean. `force` is excluded from that identity, with its own staged mechanism, and `replace_table_rls` leaves `ENABLE`/`FORCE` alone so the table is never briefly unpolicied. `audittenancy` covers a generated-but-never-applied replacement — see [`tenancy.md`](tenancy.md#auditing). `GUITARS_TENANT_POLICIES = False` emits nothing and **drops no policy already migrated**, so turning it off after a generation leaves the policies live in the database while the Python layer stops accounting for them — which reopens the owned-rule gap [`owned-relations.md`](owned-relations.md) closes, since `hard_delete()` gates on the same setting but reads it per call rather than at generation time, and so follows every relation a tenancy refusal spared. Turn it off before the first generation, or drop the policies in the migration that flips it.

## Odds and ends

`migrate` runs inside `tenancy_bypassed()` — a `RunPython` backfill under RLS otherwise matches no rows and gets marked applied anyway — so `guitars` must appear in `INSTALLED_APPS` **before** anything else defining `migrate`. Edit SQL under `src/guitars/sql/` and verify the generator still matches it; a new name needs `FROZEN_SQL_NAMES` too, and an existing value needs a down-then-up re-apply since already-migrated databases carry the old text.
