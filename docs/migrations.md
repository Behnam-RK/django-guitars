# Enforcement migrations

## Vocabulary

An **enforcement migration** is a generated migration of `RunSQL` operations, describing what the database **guarantees about the rows** (not schema, already covered by Django's own migrations) for every code path, including ones that never call `save()`. An **enforcement operation** is one `RunSQL` entry: a timestamp trigger (`_updated_at`), a soft-delete rule (`_deleted_at`), an owned soft-delete rule (`OwningForeignKey`), the statement-level owned **sweep** trigger paired with it, an MTI redirect rule/trigger, a tenant policy (RLS), or a tenant-autofill `BEFORE INSERT` trigger. All seven ship from one command sharing discovery, dedupe, scaffolding, digest stamping, and app scoping. The shape of the model *is* the opt-in — no registry.

## Generating them

`makemigrations` is extended to run the generator right after the schema migrations by default, so the two cannot drift (`--check` fails CI if either layer is missing). Set `GUITARS_AUTO_MAKE_MIGRATIONS = False` for the explicit two-command workflow instead. `LOCAL_APPS` names which apps the generator scans — a label matching no `AppConfig.name` scans nothing and `--check` exits 0, not an error.

> ⚠️ With `GUITARS_AUTO_MAKE_MIGRATIONS = False`, plain `makemigrations` does **not** create the rules. Until `makeguitarmigrations` runs and you `migrate`, `.delete()` permanently deletes rows.

## Generated migrations carry their SQL literally

A generated operation contains the statements it runs, not a reference to a library constant — until 1.1.0 the file did `from guitars import sql`, so a migration's *meaning* depended on the installed kit version: the same migration number built `<> 'on'` rules on 1.0.0 but `= 'off'` on 0.7. `guitars.sql`'s names remain a frozen interface for that committed form's sake.

## Idempotency has three layers

1. **A `[DIGEST:…]` marker** on the migration's first line identifies an unchanged *operation set* — if nothing changed, no new migration is written.
2. **Per-operation comment headers** identify which tables are already covered, so a *partially* covered app receives only what it lacks.
3. **A `[SQL:…]` identity** on each header digests that operation's SQL — what makes a changed SQL constant generate its own migration.

The third exists because the first two missed the case that mattered most: the header scan short-circuits before anything is built, so a recognised header read as covered *forever* — how the 1.0.0 soft-delete guard rewrite reached every existing database as nothing at all. A header with **no** `[SQL:…]` predates SQL inlining and reads as stale, regenerated once on 1.1.0.

> ⚠️ **Header strings are frozen.** Reword one and every existing migration stops being recognised, emitting duplicates. `tests/test_header_corpus.py` guards every scanner against the project's own committed migration history.

## Three forms

Each operation is emitted in one of three forms, chosen from what history records — `IF EXISTS`/`OR REPLACE` are claims about *knowledge*:

| Recorded | Form | Why |
| --- | --- | --- |
| nothing | plain `CREATE` | A collision must fail loudly. |
| a different/no `[SQL:…]` | `DROP`+`CREATE`, no `IF EXISTS` | Known to be ours; an unguarded drop reports drift instead of hiding it. |
| `--adopt` | `DROP … IF EXISTS`+`CREATE` | The flag's premise is that nobody knows what the database holds. |

Soft-delete rules and trigger functions are the two exceptions, always `CREATE OR REPLACE` — no instant without a rule, and `DROP FUNCTION` refuses while any trigger depends on it. `--adopt [app_label …]` exists because `create_tenant_policy` is a bare `CREATE POLICY` (no `IF NOT EXISTS`), so an unrecorded-but-real policy used to fail `migrate` with *already exists*. Cannot combine with `--force-rls` — run `--adopt` first.

## Rule names

PostgreSQL dedupes a rule on its name per table, not on what it references, so two operations resolving to one name is a **silent replacement** rather than an error — the second wins, the first relation stops cascading, and `--check` stays green over the loss. Every name folds a schema-qualified table in **length-prefixed** (`('tenant_a', 'events')` and `('tenant', 'a_events')` would otherwise meet). The cascade family adds its FK column plainly: an inbound child with two `CASCADE` foreign keys to one parent keeps the bare `soft_delete_related_<child>` for the first and takes `soft_delete_related_<child>_<fk>` for the rest, which a child table named exactly another child's `<table>_<column>` can claim twice. "For the first" is decided per *call*, and an MTI parent and its child resolve to one `owner_table`, so a model with a `CASCADE` key to each of them claims the bare name twice as well — and reaches the same dedupe *key* doing it, which is why the clash is reported on the relation and not on that key. That spelling shipped in 0.x and **cannot move** — nothing retires a rule, so renaming it would leave every migrated project's old rule live beside the new one — so the generator reports the clash instead of renaming around it, on stderr and as a `--check` failure: one of the two rules does not exist in the database the migration ships to, which is what `--check` is for. A generating run only reports, the files being written by the time it is known. The *owned* family, new in 2.3.0 and free of that history, sizes **every** variable segment — `soft_delete_owned_<n>_<target>_<n>_<fk>`, schema included — so reading each length before its segment leaves no boundary to guess at and no two `(schema, table, column)` triples can reach one name. Sizing only the last segment would not have been enough: it rules out the adjacent split (`('shop_press_kit', 'kit_id')` versus `('shop_press', 'kit_kit_id')`) while `('a_5_b', 'c')` and `('a', 'b_1_c')` still meet on `soft_delete_owned_a_5_b_1_c`. The report covers both families regardless — a proof in one is not a reason to stop watching. The **self-cascade** trigger, new in 2.8.0, sizes every segment for the owned family's reason and on that family's segments — `soft_delete_self_cascade_<n>_<schema>_<n>_<table>_<n>_<fk>` — the table its key points at being the table it fires on, so unlike the sweep there is no second table to fold in. The families' distinct prefixes are what keep them from meeting each other at all. The owned **sweep**, new in 2.6.0, sizes one segment more than the rule it accompanies — `soft_delete_owned_sweep_<n>_<owner>_<n>_<target>_<n>_<fk>`, both schemas included. A rule is namespaced per table, so the owner it fires on need not be spelled; the sweep's *function* is namespaced per schema, and two owner tables routinely share a `(target, fk)` pair, so under the rule's spelling the second `CREATE OR REPLACE FUNCTION` would overwrite the first's body and leave one table's trigger running the other's predicate. Reported the same way, on the name alone.

## Renames

PostgreSQL carries a trigger, rule or policy **with its table**, so after a `RenameModel` (or an `AlterModelTable`) the object is still there while the coverage asserting it is filed under the old table name. Before 2.9.0 the new name read as uncovered and the next run emitted a plain `CREATE`, which fails `migrate` with *trigger … already exists* — a policy the same way, `CREATE POLICY` having no `OR REPLACE`. The generator now derives `current db_table -> every name it held before, oldest first` by replaying Django's own migration state either side of each renaming operation, rather than re-deriving its naming rules: an explicit `db_table` survives a `RenameModel` untouched, and an `AlterModelTable` moves a table with no model rename at all. **Every** prior name, not just the first, because a generation that ran between two renames left an object under the intermediate one and only dropping each leaves a single object behind — and a prior name a later `CreateModel` put back in service is dropped from the chain, its coverage being live. Read off the operations rather than by diffing the two states, since a `RenameModel` changes the model name too and a diff sees one model gone and another arrived. The scan then re-keys every recorded family onto the name in use, so each family's own "recorded, but the digest moved" path fires and emits its **replace** form. A key already recorded under the new name was written after the rename and wins, so a stale one never displaces it. The families whose object *name* embeds a table — the cascade and owned rules, the owned sweep, the self-cascade trigger — need more than that, because what PostgreSQL carried over still answers to the name the old table gave it: their replace form drops every name in that chain (`IF EXISTS`, since a project that never applied the old coverage has nothing to drop) before creating the new one. Without it the sweep and self-cascade forms would fail on a name nothing has, and the two rule families would leave the carried-over rule live beside the new one, both cascading and neither retired.

## Retirement

The three forms above all *assert* an object. **Nothing else is ever retired**: no rule or trigger of the other six kinds is dropped when the model stops calling for it, so removing the field behind one makes Django's `RemoveField` fail at `migrate` (`rule … depends on column`) and relaxing one — a `CASCADE` foreign key made `SET_NULL`, an `OwningForeignKey` made plain — leaves the rule live with `--check` green. Since 2.9.0 the answer to `rule … depends on column` is **`guitars.operations.RetireEnforcement(table, column=None)`**, placed *before* the `RemoveField` (or a type-rewriting `AlterField`) in the same migration. It reads `pg_depend` — never `pg_rules.definition`, which prints identifiers unquoted and lower-cased, so a quoted match finds nothing and a bare one cannot tell `shop` from `shopping` — and drops **this kit's** rules and policies depending on that column, or on the whole table when no column is given, taking the table's own triggers and policies with it in that form. Filtered by name as well as by dependency: the operation is irreversible, so a consumer's own rule, trigger or policy is never taken — one of those blocking the same change is the consumer's to drop. It refuses rather than guessing where the table does not exist or the column does not resolve — the latter being what, before the guard, turned a typo or the operation placed after its `RemoveField` into a retirement that read as done and dropped nothing. A tenant policy is filed against the column it reads, so **either** form takes it, and with the last one goes the table's `ENABLE`/`FORCE ROW LEVEL SECURITY` and its `rls_exempt_*` policies — row-level security being a flag rather than an object `pg_depend` reaches. Any surviving policy, ours or a consumer's, keeps the flag up. `DeleteModel` needs it least: Django's `DROP TABLE … CASCADE` already takes dependent rules on every supported version, and only `RemoveField` fails, and only on Django 6.0 where `sql_delete_column` lost its `CASCADE`. It is **irreversible on purpose** — what it drops is written only by the generator, so a no-op reverse would leave history claiming objects the database no longer has with `--check` green, and on the whole-table path the missing object is the table's own `soft_delete` rule. To roll back, reverse the schema change by hand and run `makeguitarmigrations --adopt`. Relaxing rather than removing still wants a hand-written drop: an `OwningForeignKey` made plain wants a `DROP TRIGGER` and `DROP FUNCTION` for its sweep beside the `DROP RULE`, and a dropped self-referential `CASCADE` key wants that pair for its trigger with no rule to go with them. Since 2.9.0 a **cascade rule** is retired too, on positive evidence only: its key is recorded, the models no longer call for it (a `CASCADE` key relaxed to `SET_NULL`, made owning, or removed), and **both** its tables still map to local models. That last clause is the whole safety property — a table mapping to nothing is a deleted model on one reading and an app outside `LOCAL_APPS` on another, and this generator cannot tell them apart, so it is *named* with the exact `DROP RULE` instead. The `reverse_sql` recreates the rule where the column can be recovered: the `_via` form spells it in the key, and the primary form does not, so it is read back off the first remaining foreign key to that owner. Where the field is gone entirely there is nothing to rebuild, and the reverse raises rather than succeeding into a database missing a rule its history claims. A **proxy model** over a model owning the column used to earn MTI operations naming its own table as its parent, which made the enforcement migration unappliable (`trigger "updated_at_trigger" ... already exists`). Fixed in 2.9.1, and nothing is retired for it: a recorded MTI key no local model reaches through an ancestor is **named** instead, with both readings — a proxy, or a model flattened out of inheritance. Whether the object is live turns on the family and on `--adopt`: a duplicate rule is deduped by name, a duplicate trigger aborts the migration and takes any rule beside it down too, and `--adopt`'s `DROP … IF EXISTS` applies either way. So the note sends the reader to the database rather than claiming, and this command guesses at neither reading. A proxy over a *real* MTI child recorded the key its concrete child still requires, so the difference is blind to it — that one is caught from the **file** instead: one table takes one MTI operation, so a migration carrying the header twice is a proxy's copy, and that note names the migration and the app, which the record-driven one cannot. Tenant autofill triggers are the other kind that can be **retired**, because their dedupe key is `(table, function)` and the function is named after the `(dimension, column)` pair — so renaming `GUITARS_TENANT_FIELD` or a `db_column` mints a new key and orphans the old trigger, which then dereferences a dropped column and fails *every* `INSERT` on the table. A key recorded but no longer required emits `HEADER_TENANT_AUTOFILL_RETIRED` and a bare `DROP TRIGGER` (`reverse_sql` recreates it), and the scan **subtracts** that key — the only place it does, which is what makes a later re-adoption emit a plain `CREATE` rather than a drop against nothing. Idempotency is the set difference alone, not a digest comparison. Two deliberate refusals: a table no local model maps to is *named, not retired* (no app to migrate into, and no migration-state graph to ask which app owned it), and an orphaned **function** is named rather than dropped (it is inert, `DROP FUNCTION` must follow every dependent trigger, and a scoped run cannot prove an out-of-scope app has none). `--adopt` uses `DROP … IF EXISTS` but never re-retires an already-retired key, since re-asserting an *absence* would grow history on every run.

## Singletons, cross-app cascades, scaffolding

`set_updated_at()`/`set_parent_updated_at()` are shared functions with one migration each in `TRIGGER_FUNCTION_APP`, kept separate so adding MTI support doesn't re-digest the single-table function migration. Tenant autofill hosts its functions there too, but keyed by name rather than as singletons — one per distinct `(column, GUC)` pair, which is **one** for a typical project since `GUITARS_TENANT_FIELD` is project-wide. Its trigger header names the function it calls, so an app depends only on the function migrations its own triggers use. The singleton is still ensured in its host app even when a scoped run named a different app, because every other enforcement migration depends on it. A cascade rule is written into the **parent** model's migration; if that app isn't in a scoped run, it's skipped with a warning naming the app to include — the accepted "pragmatic scope" tradeoff. An *owned* rule has no such gap in **where it lands**: it fires on the declaring model's own table, so it always goes into the app being scanned. Since 2.4.0 it has a different one — its last-owner guard reads every owning column across the whole registry, so a model added in an app that *is* in scope moves the rule text of one that is not, which a scoped run will not regenerate. Warned, not escalated: an unscoped run (what CI runs) re-derives every rule. A rule's action also names tables and columns in **other** apps -- a co-owner arm's column, a cascade rule's `{related_table}` -- and PostgreSQL resolves those references when it *parses* the rule action, so they must exist by the time the migration runs. Since 2.5.0 the generator **emits a dependency edge** for each, pointing at the migration that *creates* the object rather than at the referenced app's leaf: a creating migration is always older than a rule naming it, so the edge cannot close a cycle, while a leaf edge over-constrains the graph and drags unrelated migrations forward. A reference resolving to nothing (an app with no migrations of its own) warns and emits none, and an edge the graph already implies -- a table's, where a later migration adds the column read beside it -- is dropped rather than written twice. No cycle check stands behind that: an edge at the creating migration points backwards by construction, and the one shape that genuinely cycles is the one `--check` declines to report. A tenant policy's MTI owner-join is covered on the same footing: it names the ancestor's table and tenant column at `CREATE POLICY` time, and the ancestor is `column_owner(model, field)` while the policy lands in the child's app. It is the one family rendering its table *unquoted*, so the `--check` match takes both forms. `--check` fails when a rule names a table nothing orders it against, by graph *reachability* rather than by the literal tuple, and prints the entry to paste -- a migration already recorded is skipped by the digest guard, so re-running the generator will not add it. Before 2.5.0 no edge was emitted at all and a fresh `migrate` could reach the rule first, failing with `relation ... does not exist`; see [ADR 0013](adr/0013-cross-app-migration-dependency-edges.md). The graph of ON UPDATE rules the generator refuses cycles from is read over the **whole** registry rather than the apps in scope — scoping narrows what gets written, never which rules exist, and a cycle detected from half the models would be a different set of refusals run to run. The generator rewrites a `makemigrations --empty` scaffold; one that fails after Django wrote it is left in place, carrying no `[DIGEST:…]`, so a later run can't mistake it for coverage.

## Staging row-level security

`GUITARS_RLS_FORCE` defaults to `True`. For a retrofit onto a populated database, ship inert (`GUITARS_RLS_FORCE = False`) and force later via `--force-rls`; `force`/`exempt_roles` are **literal arguments**, never read from settings at migrate time. A tenant policy's SQL depends on a variable `{dimension: column}` mapping, so its header carries a `[POLICY:<digest>]` identity separate from `[SQL:…]` — a changed identity emits a **replacement**, catching a model that gained a dimension while `--check` would otherwise report clean. `force` is excluded from that identity, with its own staged mechanism, and `replace_table_rls` leaves `ENABLE`/`FORCE` alone so the table is never briefly unpolicied. `audittenancy` covers a generated-but-never-applied replacement — see [`tenancy.md`](tenancy.md#auditing). `GUITARS_TENANT_POLICIES = False` emits nothing and **drops no policy already migrated**, so turning it off after a generation leaves the policies live in the database while the Python layer stops accounting for them — which reopens the owned-rule gap [`owned-relations.md`](owned-relations.md) closes, since `hard_delete()` gates on the same setting but reads it per call rather than at generation time, and so follows every relation a tenancy refusal spared. Turn it off before the first generation, or drop the policies in the migration that flips it.

## Odds and ends

`migrate` runs inside `tenancy_bypassed()` — a `RunPython` backfill under RLS otherwise matches no rows and gets marked applied anyway — so `guitars` must appear in `INSTALLED_APPS` **before** anything else defining `migrate`. Edit SQL under `src/guitars/sql/` and verify the generator still matches it; a new name needs `FROZEN_SQL_NAMES` too, and an existing value needs a down-then-up re-apply since already-migrated databases carry the old text.
